# D−5 / 80% 거래 실행 V2.0

앱의 거래 관리 화면은 코빗 KRW 현물과 비트겟 UTA USDT 무기한 선물을 지원한다. 공개 시세와 주문 계산은 Vercel에서 실행하고, 비밀 키·계좌 조회·주문·영구 원장·스케줄러는 고정 IP를 가진 별도 Node 실행 서버에서 실행한다. 실제 키나 실거래 서버가 없으면 화면에 미연결 상태를 표시하며 주문 API는 실패하도록 되어 있다.

## 전략 및 기존 결과와의 차이

- MACD 1: 12/26/9, 0선 상향 및 RSI > 30일 때 40%, 하향 시 현금. 연구 엔진과 같이 수집 자료 시작 후 365일 유예를 적용한다. 실제 거래소 최초 상장일을 역추정하지 않는다.
- MACD 2: 12/26/9, 양수 골든 100%·데드 50%, 음수 골든 50%·데드 0%.
- MACD 3: MACD 2 비중에 18/39/9.
- MACD 4: MACD 3의 음수 데드에서 -100% 숏. 선물 전용.
- MACD 5: 0선 상향 후 첫 양수 골든에만 +200%, 나머지는 MACD 4. 선물 전용.
- 현재 종가가 유지되는 5일 경로에서 상태 변화를 예측한다. 동일 상태·동일 사건의 과거 유사 표본 중 5일 결과가 이미 확정된 사례만 사용한다. 중첩 5일 구간은 제외한다. 최소 30개, 성공률 80% 이상이어야 선행 주문한다. 확률은 수익 확률이 아니다.
- 초기 등록은 확정된 현재 목표 비중을 배치한다. 이후 확정 신호 또는 적격 선행 신호가 있을 때 조정한다. 단순 예측일 도래로 미확정 신호를 확정으로 간주하지 않는다.
- 선행 가격: 이전 완성 일봉 종가 ± ADR(5) × [0.2, 0.5, 0.8, 1.1, 1.4]. 호가 단위의 공배수로 시작 가격과 간격을 맞춰 실제 5개 가격 간격도 동일하게 만든다. 각 주문은 동일한 결제통화 금액으로 5분할하며 수량 단위 내림으로 미세한 차이가 날 수 있다. 합계 수량은 잔량·한도 범위를 넘지 않게 조정한다. 거래소 최소 수량·금액으로 5개를 만들 수 없으면 축소된 개수로 몰래 실행하지 않는다.
- 새 완성 일봉마다 기존 앱 주문의 취소가 확정된 뒤 잔량을 재계산한다. 선행 기준 소멸 시 미체결 취소, 이미 체결된 포지션은 유지한다. 5개 선행 주문이 전량 체결되면 가격 변화만으로 그 신호를 반복 실행하지 않는다.
- 확정 신호 잔량은 현재가 기준 0.3% 가격 보호 IOC 5개로 완료를 시도한다. 과거 일봉 시가로 소급 체결하지 않는다. 같은 가격의 완료 주문이므로 이 단계의 가격 간격은 0이다. 시장가와 동일한 무제한 체결을 보장하지 않는다. 최소 주문 미달은 RESIDUAL, 장애·당일 25회 송신 한도 도달은 ERROR이며 성공으로 표시하지 않는다.
- 선물 방향 전환은 reduceOnly 청산부터 처리한다. 청산 잔량이 최소 주문 단위 아래로 남으면 반대 포지션을 강제로 열지 않는다. 거래소에서 잔량 정리가 필요할 수 있다.
- 기존 비교표 60개는 `trading/comparison.json`의 과거 검증 결과다. 한도, 거래소별 가격, 펀딩비, 유지증거금 및 실제 체결 조건을 반영한 수익률이 아니다. 실제 주문은 과거 성과표를 신호로 사용하지 않는다.

## 전체·종목별 투자 한도

한도는 KRW 현물 평가금액, USDT 선물의 **명목 포지션 금액** 기준이다. 선물 증거금 한도로 오해하면 안 된다. KRW와 USDT는 자동 환산하지 않으며 각 거래소 계좌 전체 한도를 별도로 설정한다.

보유 포지션의 절대 평가금액 합계와 신규 미체결 금액을 더한다. 숏과 롱을 상계하지 않는다. 청산 주문을 접수한 것만으로 사용액을 줄이지 않는다. 주문 전마다 실제 계좌와 미체결을 다시 확인하여 전체 한도와 해당 종목 한도를 동시에 적용한다. 계산은 decimal.js 십진수 연산이며 주문 소수 단위는 내림한다.

기준 운용금 = min(계좌 평가액, 종목 한도 ÷ 전략 최대 배수). MACD 5의 최대 배수는 2, 나머지는 1이다. 최대 노출이 2배여도 명목금액 한도를 넘지 않게 하며 비용 및 가격 여유 0.5%를 둔다. 예: 비트겟 종목 한도 10,000 USDT이면 MACD 5의 기준 운용금은 최대 5,000 USDT이고 +200% 목표는 최대 10,000 USDT 범위다.

가격 상승만으로 한도를 초과하면 신규 투자를 막는다. 자동 강제 청산은 하지 않으며 감소 주문은 허용한다. 실시간 평가금액 자체가 항상 한도 이하라는 보장은 아니다. 외부에서 동시에 수동 주문이나 다른 봇을 실행하면 앱의 계좌 검증 사이에 잔고가 바뀔 수 있으므로 전용 계좌를 사용한다.

## 실행 서버 설정

1. Node 22.13 이상(검증 환경 Node 26)과 영구 디스크를 가진 고정 IP 서버에 저장소를 배치한다. `npm ci` 실행. SQLite 파일은 임시/서버리스 디스크에 두지 않는다.
2. `.env.example`을 `.env`로 복사하고 안전한 서버 환경에서만 비밀 값을 설정한다. `.env` 및 원장 파일은 git에서 제외된다. `.env`를 웹 서버 문서 루트에서 제공하면 안 된다.
3. `TRADE_GATEWAY_TOKEN`과 `TRADE_OPERATOR_TOKEN`은 서로 다른 32자 이상의 무작위 값이다. 거래소 키와도 달라야 한다. 관리자 토큰은 브라우저 접속용, 게이트웨이 토큰은 Vercel과 실행 서버 사이용이다.
4. 코빗 HMAC API 키의 허용 IP에 실행 서버의 고정 출구 IP를 등록한다. 잔고 조회·주문 조회·주문 신청 권한만 부여한다. 출금 권한은 필요 없다. 코빗 공식 문서: https://docs.korbit.co.kr/llms/en/rest_api.md
5. 비트겟 UTA API 키/secret/passphrase를 설정한다. USDT 선물 전용 계좌, 단방향·종목별 격리·레버리지 2배가 필요하다. 앱은 모드나 레버리지를 임의 변경하지 않는다. 다른 결제통화 포지션·주문이나 부채가 있으면 거절한다. 공식 문서: https://www.bitget.com/api-doc/uta/guide 및 https://www.bitget.com/api-doc/uta/trade/Place-Order
6. 처음에는 거래소에서 별도로 발급한 **데모 키**와 `BITGET_DEMO=true`, `TRADING_ENABLED=true`로 비트겟 데모를 연결한다. `paptrading: 1` 헤더를 사용한다. 코빗은 같은 설정에 영향을 받지 않으므로 코빗 실키를 함께 설정하고 코빗 캠페인을 시작하지 않는다. 로컬 자동 테스트는 키 없이 별도 가짜 어댑터만 사용한다.
7. `npm run start:trading`으로 실행한다. 서버 기본 바인딩은 127.0.0.1:4190이다. HTTPS 역방향 프록시 뒤에 두고 `/command`만 접근시키며 정상적으로 재시작·지속 실행되는 서비스로 등록한다. 거래소 IP 허용 설정과 TLS는 운영 환경에서 확인해야 한다.
8. Vercel 환경에 `TRADE_GATEWAY_URL`, `TRADE_GATEWAY_TOKEN`, `TRADE_OPERATOR_TOKEN`, `TRADING_ALLOWED_ORIGIN=https://coin-signal-v1-04.vercel.app`를 설정하고 재배포한다. Vercel에 거래소 비밀 키를 넣을 필요가 없다.
9. 앱에서 관리자 접속 → 계좌 전체·종목 한도 저장 → 실계좌 미리보기 → 데모 자동매매 시작 → 원장과 거래소 내 체결을 대조한다. 첫 역사 수집은 시간이 걸릴 수 있다. 미리보기 응답이 지연되면 잠시 후 다시 미리보기하고 중복 시작 버튼을 누르지 않는다.
10. 데모에서 실거래로 바꾸기 전에 앱 캠페인을 모두 중지하고 미체결 취소를 확인해야 한다. 연결 계정 또는 데모 모드가 바뀌면 진행 중인 캠페인을 이어 실행하지 않는다. 실제 운영은 서버에서 `BITGET_DEMO=false`, 실키, `TRADING_ENABLED=true`, `BITGET_LIVE_ENABLED=true`를 설정한 뒤 다시 서버를 시작하고 앱에서 명시적으로 캠페인을 등록한다. 실제 자산 주문이 발생한다. 코드 배포 자체는 이러한 설정을 켜지 않는다.

## 복구 및 운영

- SQLite 독점 잠금으로 같은 원장에 두 실행 프로세스가 붙는 것을 막는다. 복제 서버/다른 원장으로 같은 거래 계좌를 동시에 운영하면 안 된다.
- 각 주문은 UUID 기반 고유 client ID와 SUBMITTING 기록을 먼저 저장한 뒤 한 번만 송신한다. 응답이 불명확하면 재송신하지 않고 거래소 주문 조회로 확인한다. 조회 실패가 지속되면 ERROR로 신규 주문을 막는다.
- ERROR 상태는 신규 주문을 재개하지 않고 잔존 앱 주문의 취소를 계속 확인한다. 화면에서 원장·거래소를 대조하고 중지 완료 후 새 미리보기로 재등록한다. 원장 파일 삭제로 잠금을 우회하지 않는다.
- 한도 변경 시 등록된 앱 미체결 주문 취소를 먼저 확인한다. 실행 도중 응답 실패가 나면 서버 상태를 재조회한다.
- 중지는 앱의 미체결 주문만 취소하고 보유 포지션은 유지한다. 전역 실행을 끄면 다음 스케줄에서 앱 주문 취소를 시도하지만 거래소 장애 시 취소 완료를 보장하지 않는다. 거래소에서도 직접 상태를 확인할 수 있어야 한다.
- 주문 체결 및 취소 상태는 약 15초마다 확인한다. 장애·유동성 부족·급변·청산·최소 주문 단위 때문에 D0 전량 완료는 보장되지 않는다. 펀딩·수수료는 실제 잔고와 거래소 응답에 반영되며 기존 연구 수익률에 소급 혼합하지 않는다.
- 운영 전 남은 검증: 사용자 데모/실계좌 권한·IP·계좌 모드 확인, 실제 부분 체결 및 유지증거금/청산 검증, 장시간 운영과 장애 복구. 현재 자동 테스트만으로 이를 완료했다고 간주하지 않는다.

## 코드

`trading/research.mjs`: 기존 MACD 1~5 재현 및 D5 조건 엔진. `trading/decision.mjs`: 완성 일봉 검증과 최신 결정. `trading/policy.mjs`: 십진수 주문·한도 계산. `server/exchanges.mjs`: 공식 REST 어댑터. `server/controller.mjs`: 지속 실행 및 확인. `server/store.mjs`: 영구 원장. `api/trading.js`: 동일 출처·관리자 세션·게이트웨이. `api/exchange.js`: 공개 시세. `trading/dashboard.mjs`: 전체 앱 공통 거래 화면.
